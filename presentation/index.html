WebGL — realistic drum construction

Each drum = composite group:

  • Cylindrical shell (PBR metalness/roughness)
  • Top + bottom chrome hoops (torus)
  • Flat drum head (disc mesh, velocity-compressible)
  • 6–10 tensioning lugs (boxes)
  • Optional stand/legs

Cymbals = thin tapered disc + bell dome,
tilted in two axes.

function buildDrumTop({ radius, height, ... }) {
  const body = new THREE.Group();
  body.rotation.x = tiltX;          // forward tilt

  body.add(shell);                  // cylinder
  body.add(topRim);                 // torus
  body.add(botRim);
  body.add(head);                   // circle disc
  addLugs(body, 6, radius, height);

  return {
    group, body, head,
    localHitCenter, localHitNormal,
    hitRadius
  };
}

Collision — swept plane

The single most important piece of the interaction layer.

Each instrument exposes a playable plane:

  • world centre c
  • unit normal n̂
  • radius r

Each frame, compute signed distances:

dPrev = (p_prev - c) · n̂
dCurr = (p_curr - c) · n̂

if (dPrev > 0 && dCurr ≤ 0) {
  // stick crossed into the surface
  t = dPrev / (dPrev - dCurr);
  contact = lerp(p_prev, p_curr, t);
  v_n = (dPrev - dCurr) / dt;
}

Hit accepted iff:

  1. Segment crosses the plane (dPrev > 0, dCurr ≤ 0)
  2. Contact point lies within radius r
  3. Normal-velocity vn exceeds threshold

Velocity is the normal component of motion → a sideways cymbal swish reads as soft, a direct hit reads as hard. Works for any surface orientation.

Why not bounding spheres?

Naive approach

"Inside sphere AND moving downward"

  • ❌ Tall cymbal bounding sphere fires on horizontal motion
  • ❌ Only detects downward Y movement
  • ❌ No sense of where on the surface
  • ❌ Hit position = drum's centre, not the stick's contact point

Swept plane

  • ✓ Works for any surface orientation
  • ✓ Velocity = component along n̂
  • ✓ Exact contact coordinates
  • ✓ Rim vs centre distinguishable by radial distance

Particle system

  • 400-particle pre-allocated ring buffer
  • Single THREE.Points draw call
  • Emit at contact point, not drum centre
  • Velocity = normal-outward + tangential spray
  • Gravity + air drag → realistic arcs

Cymbal hits spray sideways; drum hits puff upward — all from the same code path, driven by each surface's own n̂.

// Two tangent axes perpendicular to n̂
_tanA.crossVectors(normal, axis).normalize();
_tanB.crossVectors(normal, _tanA).normalize();

// Mostly along normal, splash tangentially
pVel[i3+0] = n.x * vn + _tanA.x * rx + _tanB.x * ry;
pVel[i3+1] = n.y * vn + _tanA.y * rx + _tanB.y * ry;
pVel[i3+2] = n.z * vn + _tanA.z * rx + _tanB.z * ry;

Web Audio — the fast path

Low-latency headset sound, fully in-browser:

  • Master bus → DynamicsCompressor → destination
  • Per-hit voice: oscillators + filtered noise
  • StereoPannerNode from hit X-coordinate
  • Velocity-scaled peak gain

Runs on the Pico's browser audio. Pd runs in parallel on the PC for the richer sound.

const osc = ctx.createOscillator();
const g   = ctx.createGain();
osc.frequency.setValueAtTime(f0, t);
osc.frequency.exponentialRampToValueAtTime(
  f1, t + decay
);
g.gain.setValueAtTime(gain * v, t);
g.gain.exponentialRampToValueAtTime(
  0.001, t + decay
);
osc.connect(g).connect(panner);

Pure Data — dataflow programming

Pd is a visual dataflow language for real-time audio:

  • Programs = boxes (objects) + cords (edges)
  • Two rates: message (events) and audio (~689 Hz blocks of 64 samples)
  • No call stack — data simply flows
  • Edit while running — changes take effect at the next block

Our patch follows a classic three-stage pipeline:

  1. Input: OSC → unpack → route by name
  2. Voicing: 8 sample-player subpatches
  3. Mix: shared stereo bus → limit → dac~

The structure is the documentation.

Pd — OSC input & dispatch

[netreceive -u -b 8000]           ; UDP listener
         │
[oscparse]                        ; raw bytes → typed list
         │
[route /drum/hit]                 ; drop non-hits
         │
[unpack s f f f f]                ; name, velocity, x, y, z
 │ │ │ │ │
 │ │ [s hit-x] [s hit-y] [s hit-z]
 │ │
 └─┴──► [pack s f] ──► [route bassdrum snare hitom ...]
                                   ▼     ▼     ▼
                             [s fire-bassdrum]   × 8

[unpack]'s right-to-left firing order guarantees all data is latched before the instrument name fires its router outlet.

3-layer velocity crossfade

Three recordings of the same drum at different intensities.
Play all three simultaneously, gated by weights that sum to 1:

soft  = max(0, 1 - 2v)
med   = min(2v, 2(1-v))
hard  = max(0, 2v - 1)
  • v = 0.25 → 50% soft + 50% med
  • v = 0.50 → 100% med
  • v = 0.75 → 50% med + 50% hard

The attack timbre changes with velocity, not just loudness — what a real drum does but single-samples can't.

Voice abstraction

Pd abstractions = reusable subpatches. Argument $1 is the drum name, substituted at instantiation.

[r fire-$1]                           ; e.g. fire-bassdrum
    │
[t f f f]                             ; forward velocity to 3 layers
 │  │  │
 │  │  └─► [t b f] → [expr max(0, 2*$f1-1)]   ; hard gain
 │  │         │        │
 │  │    [tabplay~ $1-hard]─►[*~]─────┐
 │  │
 │  └────► ... med layer ...           │
 │                                      ▼
 └───────► ... soft layer ...  ──► [+~] → [*~ 0.9] → [throw~ mix-L/R]

Main patch instantiates: [voice-multi bassdrum], [voice-multi snare], [voice-multi hihat].

Spectator mirror

Desktop browser shows the VR user's view live:

  • Same main.js, boolean isSpectator toggles behaviour
  • VR client emits pose every other frame via volatile Socket.IO
  • Spectator camera matches the VR headset's pose
  • Two translucent "ghost" drumsticks show hand positions
  • Visual hit feedback mirrored; sound stays on VR side
socket.volatile.emit('xrPose', {
  cam: {
    px, py, pz,
    qx, qy, qz, qw
  },
  ctrl: [c0Pose, c1Pose]
});

Performance budget

Target: stable 72 Hz on Pico XR2 Gen 1

  • ≈ 2,500 triangles total across all instruments
  • ≈ 30 draw calls
  • 5 lights (1 ambient + 4 point)
  • 400 particles (ring buffer, one Points draw call)
  • Pixel ratio capped at 2×
  • Pose data throttled to ~36 Hz
  • Environment IBL pre-rendered once at startup
